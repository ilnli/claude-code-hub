# 成本感知的 Provider 权重调整规则

## 状态

本文记录 2026-08-06 访谈确认的功能设计。它描述行为契约和建议实现边界，不代表功能已经实现。

## 目标

管理员可以创建规则，显式选择一组 Provider，并让系统根据已有的 `costMultiplier`
定期重算这些 Provider 的路由 `weight`。成本倍率越低，规则内相对权重越高。

本功能只修改路由权重：

- 不修改或同步 `costMultiplier`；
- 不处理现有权重写入约束或旧管理接口；
- 不按用户组有效优先级计算；
- 不因成本倍率变化立即触发；
- 不清理现有粘性 Session 或前缀亲和关系，权重只影响之后需要重新选路的请求。

## 规则和成员

### 规则

- 规则只能由现有管理员通过 Dashboard 或管理 REST API 管理。
- 名称必填且在未删除规则中全局唯一；描述可选。规则删除后名称可立即复用。
- 创建时先选择一个精确的公开 `providerType` 和一个全局 `priority`，再添加成员。
- 规则存在成员时，不能修改 `providerType` 或全局 `priority`。
- 规则最多包含 500 个成员。
- 允许保存零个或一个有效成员的停用草稿。
- 同一类型和全局优先级可以存在多条规则，但同一个 Provider 最多属于一条规则。
- 不提供“移动成员”操作；管理员先从旧规则移除，再添加到新规则。

### 成员资格

- 成员由管理员以稳定 Provider ID 显式添加，不再使用默认全选或排除列表。
- 添加的 Provider 必须与规则具有相同的精确 `providerType` 和全局 `priority`。
- 可以添加已禁用 Provider；它保留成员关系，但只在重新启用后进入计算。
- Provider 被禁用时保留成员关系；被重新启用后自动恢复参与。
- Provider 的类型或全局优先级发生变化，或 Provider 被删除时，自动移出规则；最后权重不恢复。
- 熔断、金额限流、活动时间窗、并发上限和临时探测状态不影响成员是否参与，只要 Provider 已启用且其他数据有效。
- 用户组 `groupPriorities` 不影响规则成员或计算；规则只认全局 `priority`。

### 独立比较域

每条规则都是独立的成本比较域。即使两条规则的类型和全局优先级相同，也不会跨规则归一化。

例如：

```text
规则 A 成本：0.1、0.2 -> 权重约：67、33
规则 B 成本：1、2     -> 权重约：67、33
```

四个 Provider 在真实选路中仍可能处于同一优先级池，但规则 A 与规则 B 的成本倍率不互相比较。

## 权重计算

### 有效参与者

一次计算只使用规则内同时满足以下条件的 Provider：

- 已启用；
- 仍匹配规则的精确类型和全局优先级；
- `costMultiplier` 是可解析、有限且大于 0 的数值。

禁用或成本倍率无效的成员保留当前权重，不进入本次归一化。有效参与者少于两个时不计算任何权重。

### 公式

对有效参与者 `i`：

```text
raw_i = 1 / costMultiplier_i
meanRaw = sum(raw_i) / participantCount
unboundedWeight_i = 50 * raw_i / meanRaw
weight_i = clamp(round(unboundedWeight_i), 1, 100)
```

规则如下：

- 取整前，规则内平均权重归一到 50；
- 使用普通四舍五入；
- 最终权重钳制在 `1..100`；
- 触发边界后不进行二次再分配，成本差异优先于最终平均值恰好为 50；
- 每次运行使用一个一致的成本倍率快照；运行期间的新倍率在下次运行生效；
- 只更新权重实际发生变化的 Provider；整组无变化时不写 Provider、不更新 `updatedAt`、不发布缓存失效。

示例：

```text
成本倍率：0.1、0.2、0.4
最终权重：86、43、21

成本倍率：0.2、0.2、0.2
最终权重：50、50、50
```

### 原子性

- 一条规则的一次权重变更是一个原子事务；任一 Provider 写入失败则全部回滚。
- 管理员修改成员或手工修改受管理权重时，管理员操作优先；并发中的规则事务检测到变化后整组回滚。
- 规则状态和成员变更递增内部 revision；后台运行提交前必须确认 revision 未变化。该 revision
  用于后台并发保护，不引入面向多个管理员的编辑合并流程。
- 同一周期内不自动重试失败运行；等待下个周期或管理员手工执行。
- 数据库提交后才发布 Provider 缓存失效。
- 数据库已提交但缓存失效失败时，不补偿回滚；运行状态为“成功但有警告”，权重等待现有缓存自然过期。

## 生命周期

### 创建、启用和停用

- 保存规则时重新校验最新成员并返回最新预览。
- 新规则至少有两个有效成员时初始启用，否则保存为停用草稿。
- 已有停用草稿补足成员后仍保持停用，必须由管理员明确启用。
- 单条启用和“全部启用”都重新校验；只启用至少有两个有效成员的规则，并返回未启用规则及原因。
- 已启用规则后来不足两个有效成员时保持启用，但该次周期不执行权重变更。
- 不设置独立的系统总开关；提供“全部启用”和“全部停用”。
- 全部停用允许已经开始的运行完成，只阻止后续周期运行。
- 停用或删除规则不恢复权重。
- 规则存在活动运行时拒绝删除。
- 删除规则后，其运行历史和规则名称/作用域快照仍保留至正常过期。

### 成员编辑

- 添加或移除成员不改变规则当前的 `nextRunAt`，新成员集合从原定下次运行开始使用。
- 执行期间发生成员编辑时，管理员编辑成功，后台运行整组回滚。
- 被移出的 Provider 保留当前权重。
- 重新添加 Provider 表示重新接受自动管理；当前手工权重保留到规则下次运行。

### 手工修改 Provider 权重

对于启用规则的成员：

- Dashboard 保存前显示规则名称和“保存后将移出规则”的二次确认；
- 管理 API 默认返回冲突，调用方必须显式声明脱离规则；
- 批量编辑的预览列出受影响的 Provider 和规则；确认后原子执行“移出成员 + 修改权重”；
- 并发时手工修改优先，规则运行整组回滚。

对于停用规则的成员：

- 手工修改权重不会移出规则，也不要求脱离确认；
- 重新启用时预览手工值和预计值；等待完整周期后，首次运行按公式覆盖手工权重。

## 调度

### 系统周期

所有规则共用一个管理员选择的周期时长，但每条规则维护自己的到期时间。预设值为：

```text
10 分钟
30 分钟（默认）
1 小时
6 小时
24 小时
```

- 新建为启用状态或重新启用后，`nextRunAt = 操作时间 + 当前系统周期`。
- 管理员修改系统周期后，所有启用规则从保存时刻重新计算一个完整新周期，不立即执行。
- 成本倍率变化不触发运行。
- 服务停机或调度故障错过周期后不补跑；恢复后等待一个完整周期。
- 多实例只允许一个执行者；协调能力不可用时跳过该次周期，不退化为每实例执行。
- 同一规则未完成时到达下一个周期，跳过重叠周期，不排队、不并发。

### 手工立即执行

- 启用或停用规则都允许管理员手工立即执行；停用规则运行后仍保持停用。
- 手工执行前同步校验有效参与者；少于两个时直接返回最新预览，不创建运行，也不发送通知。
- 同一规则正在运行时拒绝新请求，并返回当前运行信息。
- 手工执行 API 要求幂等键；同一规则和幂等键返回同一个运行。
- 对已启用规则，手工请求受理时设置 `nextRunAt = requestedAt + 当前系统周期`；停用规则不设置
  周期到期时间。手工执行不改变系统周期时长。

## 预览和管理界面

Dashboard 和管理 REST API 支持：

- 规则 CRUD；
- 成员添加和移除；
- 单条启停、全部启用、全部停用；
- 调整预览；
- 手工立即执行；
- 最近运行状态和七天历史；
- 系统周期选择。

预览只显示规则成员，不显示同类型、同优先级的非成员。至少包括：

- 成员启用状态；
- 当前成本倍率及无效原因；
- 当前权重和预计权重；
- 规则内预计占比 `预计权重 / 本规则预计权重总和`。

“规则内预计占比”必须明确标注为规则内部比例，而不是实际全局流量概率。

所有用户可见字符串必须通过现有五语言 i18n 体系提供。

## 运行历史、审计和通知

### 运行历史

- 每次已创建的运行保存摘要。
- Provider 明细只保存实际变化、跳过和失败项，不保存无变化明细。
- 历史固定保留七天，不提供可配置保留期。
- 删除规则不提前删除历史；历史保存不可变规则 ID、名称和作用域快照。

### 管理审计

以下操作写入现有管理审计日志：

- 规则创建、编辑、删除；
- 单条和批量启停；
- 成员添加、移除和自动移除；
- 系统周期修改；
- 手工立即执行；
- 手工改权重导致的成员脱离。

### 通知

复用现有通知绑定和 Webhook，不创建独立通道。以下情况打开故障状态并发送一次汇总通知：

- 已创建的周期或手工运行发生权重事务失败；
- 已启用规则到期，但因协调失败、调度异常、运行重叠、成员不足或全部成员无效等原因未执行；
- 数据库提交成功但缓存失效失败，运行状态为“成功但有警告”。

持续相同故障不按周期重复通知。下一次完全成功的运行发送恢复通知并清除故障状态，即使该次没有权重变化。

以下情况不发送通知：

- 正常成功并修改了权重；
- 正常成功但没有权重变化；
- 手工执行在创建运行前因有效成员不足而同步拒绝。

## 建议实现边界

### 持久化

建议使用规范化关系保存：

- 规则：名称、描述、精确类型、全局优先级、启用状态、内部 revision、下次到期时间、故障状态和审计字段；
- 成员：规则 ID 与 Provider ID，并对 Provider ID 设置跨规则唯一约束；
- 运行：触发来源、幂等键、状态、规则快照、摘要、开始和完成时间；
- 运行明细：变更、跳过或失败的 Provider 快照；
- 系统设置：全局周期预设值。

数据库结构必须通过修改 `src/drizzle/schema.ts` 后运行 `bun run db:generate` 生成迁移，不能手工创建迁移文件。

### 后台服务

- 调度生命周期可参考现有上游成本倍率探测调度器。
- 本功能的多实例协调必须失败关闭；协调存储不可用时不能退化为每进程执行。
- Provider 写入成功后必须发布现有跨实例 Provider 缓存失效。
- 七天运行历史清理复用现有后台队列/清理任务模式。

### 测试重点

新功能单元测试覆盖率至少 80%，并覆盖：

- 等成本、低于 1 的成本、极端成本和边界钳制；
- 无效成本、禁用成员和有效成员不足；
- 多规则独立归一化和成员跨规则唯一性；
- 原子回滚、管理员并发修改优先和缓存警告；
- 周期变更、错过周期、运行重叠和手工幂等；
- 启用/停用规则下手工改权重的不同脱离行为；
- 故障去重与成功恢复通知；
- REST API、Dashboard 交互和五语言 i18n。
